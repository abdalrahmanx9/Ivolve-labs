The Core Idea & Concepts

If you've ever compiled a Java file by typing javac Main.java in your terminal, you know it works for one file. But what happens in a real company where your project has 50 files and needs 15 outside libraries (like database drivers, JSON parsers, or testing tools)?

Without a build tool, you would have to search the internet, download 15 .jar files by hand, put them into a folder, and type a 200-character terminal command just to compile. If one library needs another library, you get stuck in what developers call "dependency hell".

This is where Maven comes in:

  • One Shopping List (pom.xml): You write down the name and version of the libraries you need. Maven goes to the central internet warehouse (Maven Central) and downloads them for you automatically.
  • Fixed Standard Folders: In every Maven project in the world, source code is in src/main/java, tests are in src/test/java, and build outputs go into target/. You never have to guess where files are.
  • The Build Lifecycle (Step-by-Step): Maven runs in predictable phases: it compiles your code, runs your tests with JUnit, and packages everything into an executable .jar file. If a test fails, Maven stops immediately so you never accidentally ship broken code.

The Core Idea & Concepts

Maven is great, but its XML files can get very long and messy. Also, Maven rebuilds everything from scratch each time. If your project takes 20 minutes to compile, waiting that long every time you change one line of code slows you down.

Gradle was created to solve this:

  • No Rigid XML: Gradle uses readable code (Groovy or Kotlin) in a file called build.gradle instead of XML.
  • Smart "Incremental" Builds: Gradle checks what changed since the last build. If you didn't touch a file, Gradle marks it as UP-TO-DATE and skips it. This makes builds up to 10x faster than Maven.
  • The Background Daemon: Gradle keeps a small worker process running in the background on your computer so it doesn't have to start up the JVM from zero every time you run a command.
  • Slide note: The slide title mentions Go with Gradle, but the lab uses Gradle to compile the Java calculator. Gradle can build Go, C++, or Android apps, but here we focus on comparing how Gradle builds the same Java app compared to Maven.

The Core Idea & Concepts

Imagine you want to give your Java calculator to a friend to run on their computer. You have two choices:

  • Choice A (Build Inside Docker): You give your friend the raw source code and tell Docker to download Maven, compile the code, and run it.
    The Good: Your friend does not need Java or Maven installed on their laptop—Docker does everything.
    The Bad: The final Docker image is huge (534 MB) because it has to carry the compiler, Maven tools, source files, and temporary caches that you never need when just running the app.
  • Choice B (Build Locally): You compile the code on your own laptop first using mvn package to make a tiny 3.7 KB calculator.jar file. Then you give Docker just that JAR file and a lightweight Java runtime (JRE).
    The Good: The image is almost half the size (296 MB), starts faster, and is much more secure.
    The Bad: Whoever builds the image must have Maven and Java installed on their machine first.
  • Why Non-Root User? By default, Docker runs everything as the root user (the super administrator). If a hacker finds a bug in your app, they might take over the entire host machine. Creating a simple unprivileged user named app stops this.

#   groupadd -r app   : -r creates a system group (low GID, no password aging)

# Copy application source code into the container image:
#   --chown=app:app : Directly sets file ownership on copy, preventing an extra RUN chown layer

# Drop root privileges and switch runtime context to non-root user
USER app

# Compile and package the Java application:
#   -B : Batch / Non-Interactive mode (silences progress bars and disables interactive prompts)

# Document network port listening inside container (informational metadata)

#   java -jar target/calculator.jar : Launches the built executable JAR

The Core Idea & Concepts

In Lab 3 we saw that building inside Docker made a big 534 MB image, while building locally made a 296 MB image. But what if your production server or CI pipeline doesn't have Maven installed?

Multi-Stage Builds solve this problem completely:

  • Two Rooms in One House: In your Dockerfile, you can have two FROM lines.
    • Stage 1 (The Kitchen): Takes the heavy Maven image, compiles your code, and creates the JAR.
    • Stage 2 (The Dining Table): Starts with a super clean, tiny Alpine Linux JRE image. You reach into Stage 1, grab only the compiled JAR file, and throw away Stage 1 completely!
  • What is Alpine Linux? Normal Linux distributions like Ubuntu or Debian weigh 100+ MB before you even add an app. Alpine Linux is a stripped-down Linux that weighs only 5 MB.
  • Saving Images as Files (docker save / load): How do you move a Docker image to a secure server that has no internet access? You can't use Docker Hub. Instead, docker save packs the image into a .tar zip archive. You copy the file with a USB stick or SCP, and run docker load on the other machine.

# STAGE 1: Builder environment — named 'build' so subsequent stages can reference artifacts
#   AS build : Assigns an alias to this initial build stage
FROM maven:3.9.15-eclipse-temurin-17-alpine AS build
WORKDIR /app
COPY . .
#   -B : Batch mode (non-interactive, suppresses transfer progress output)
RUN mvn package -B

# STAGE 2: Clean, minimal production runtime
FROM eclipse-temurin:17-jre-alpine

# In Alpine (musl libc / busybox), create system group and user:
#   -S     : Create a system group / system user (low UID/GID < 1000)
#   -G app : Assign primary group 'app' to the user
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app

# Copy ONLY the compiled JAR from Stage 1 into Stage 2:
#   --from=build    : Reach into the 'build' stage container filesystem
#   --chown=app:app : Set ownership directly to non-root user during copy
COPY --from=build --chown=app:app /app/target/demo-0.0.1-SNAPSHOT.jar app.jar

USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

#   -t image2              : Target image name
#   -f Dockerfile.optimized: Use custom Dockerfile path instead of default ./Dockerfile
#   .                      : Build context

# Size check: 210 MB (Down from 420 MB - exactly 50% cut!)

#   -d           : Detached background execution

#   -p 8080:8080 : Map host port 8080 to container port 8080

The Core Idea & Concepts

When you write FROM node:18 in your Dockerfile, you aren't just downloading Node.js. You are downloading an entire operating system (like Debian) with hundreds of pre-installed system packages: bash, curl, OpenSSL, git, and python.

If that base image is a few years old, security researchers have already discovered bugs in those packages. Attackers use these bugs (called CVEs — Common Vulnerabilities and Exposures) to hack into your servers.

How Trivy helps:

  • The Scanner: Trivy inspects every package inside your image and checks it against a giant security database. It rates bugs as LOW, MEDIUM, HIGH, or CRITICAL.
  • How to Fix 2,000+ Vulnerabilities:
    1. Upgrade your base image: Moving from an old Debian image to a modern node:22-alpine cuts out 95% of security bugs because Alpine has far fewer packages installed.
    2. Upgrade outdated packages: Upgrade packages like Express to the latest patch release.
    3. Delete tools you don't need: Production containers only need to run your code with node app.js. They do not need npm or npx inside them anymore! Deleting npm removes its hidden bundled bugs too.

The Core Idea & Concepts

  • Volume vs Bind Mount:

    • Host Bind Mount: Links an exact folder on your laptop (e.g. ./backend-data) into the container. When the container writes messages.json, you can see and edit the file directly on your desktop.

  • Why do we need Calico CNI? By default, Kubernetes nodes cannot route traffic between pods on different servers. Calico acts like an internal private highway (overlay network) giving every pod its own IP address across the entire cluster.

net.bridge.bridge-nf-call-iptables  = 1

🏷️ Node Isolation Using Taints and Labels in Kubernetes

Objective: Reserve specific worker nodes for dedicated projects by repelling unwanted pods with Taints and attracting target pods with Labels.

📋 Lab Prompt & Requirements (Slide Task)

The Core Idea & Concepts

Imagine your company has 10 general servers and 1 expensive server with high-speed SSDs dedicated to Project iVolve. If developers start launching test apps, Kubernetes might blindly put random test pods on your expensive server, wasting its capacity.

We use a two-part lock-and-key system to solve this:

  • Part 1: The Taint (The Repellent / Keep Out Sign): You put a taint (workload=ivolveApp:NoSchedule) on the node. Now, the Kubernetes scheduler will refuse to put any pod on that node. Pods are repelled.
  • Part 2: The Toleration (The VIP Pass): You give your project pods a special VIP pass called a Toleration. Now they are permitted to land on the tainted node.
  • Part 3: The Label & NodeSelector (The Target Magnet): A toleration only means "I am allowed here"—it does not force the pod to go there. Adding project=ivolve on the node and nodeSelector: project: ivolve on the pod actively guides the pod to that specific machine.

💾 Persistent Storage Setup for Application Logging

Objective: Ensure application logs survive container crashes by binding a hostPath PersistentVolume with a PersistentVolumeClaim.

  • • Size: 1Gi

  • • Access mode: ReadWriteMany (to allow all replicas read/write access)
  • • Reclaim policy: Retain

The Core Idea & Concepts

Containers are temporary (ephemeral). When a container restarts, crashes, or updates to a new version, every file written inside it is deleted.

If your app writes access logs to /app/logs, you will lose all audit history whenever a pod restarts. Kubernetes solves this by separating storage into two roles:

  • PersistentVolume (PV) - The Hard Drive: A real storage volume created on the cluster. In this lab, it points to a real folder on the physical node (/mnt/app-logs).
  • PersistentVolumeClaim (PVC) - The Voucher / Request: The application developer does not need to know where the physical hard drive is. They just say: "I need a 1 GB drive with ReadWriteMany access."
  • The Binding: Kubernetes automatically finds a PV that matches the PVC's request and permanently marries them together (Status: Bound).

The Core Idea & Concepts

Why can't we use a normal Deployment for a database like MySQL?

  • Deployments are for Anonymous Workers: In a Deployment, pods get random names (like app-7dfb8-xk2). If a pod dies, the replacement gets a new random name. That's fine for web servers, but terrible for databases.
  • StatefulSets are for Identifiable Leaders: In a StatefulSet, pods get ordered, predictable names starting from 0: ivolve-db-0. If ivolve-db-0 crashes, it is recreated with the exact same name ivolve-db-0 and automatically re-attaches to its exact same hard drive!
  • What is a Headless Service? A normal Kubernetes service gives you one shared IP that randomly balances traffic. A Headless Service (clusterIP: None) tells the internal CoreDNS server: "Give this specific database pod its own direct DNS name: ivolve-db-0.ivolve-db-svc.ivolve.svc.cluster.local."

The Core Idea & Concepts

How does Kubernetes keep pods from fighting over CPU and memory?

  • Requests (The Guaranteed Reservation): This is the minimum amount of CPU and RAM your pod needs to survive. The scheduler uses requests to find a node that has enough spare room.
  • Limits (The Ceiling): This is the maximum amount your pod is allowed to use. If your pod tries to consume more CPU than its limit, Linux throttles it. If it tries to consume more memory than its limit, Linux terminates it (OOMKilled).
  • The Rolling Update Quota Deadlock:
    • In Lab 11, we set a ResourceQuota of 3 pods maximum.
    • Currently running: 2 app pods + 1 MySQL pod = 3 pods (100% full).
    • When you update a Deployment, Kubernetes starts a new surge pod before killing the old one to avoid downtime.
    • But the 4th pod is rejected by the quota! The deployment gets stuck in a deadlock until you increase the namespace quota headroom to 5 pods.

🔒 Control Pod-to-Pod Traffic via Network Policy

Objective: Block unauthorized access to MySQL by creating an in-cluster firewall policy that allows traffic only from your Node.js application pods.

📋 Lab Prompt & Requirements (Slide Task)

  • • Name: ivolveNP
  • • Pod Selector: Targets mysql pod.
  • • Policy Types: Only Ingress
  • • Ingress Rule:
  • ✓ Allows traffic only from the application pods.
  • ✓ Restrict access to port 3306 (MySQL default port).

The Core Idea & Concepts

By default, Kubernetes network security is wide open: any pod in the entire cluster can connect to any other pod. If an intern or compromised app in another namespace knows MySQL's IP, they can connect directly to your database.

A NetworkPolicy is a firewall for Kubernetes pods:

  • The moment you attach a NetworkPolicy to your MySQL pod, it enters Default-Deny mode. All incoming traffic is blocked.
  • Then you punch one single hole in the firewall: "Allow traffic on port 3306, but ONLY from pods that have the label app: ivolve-app."
  • Any other pod that tries to connect gets timed out and dropped.

Unauthorized Pod

Connection Timed Out
Blocked by Calico CNI firewall enforcement.

1. Create the NetworkPolicy Manifest

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ivolve-np
  namespace: ivolve
spec:
  podSelector:
    matchLabels:
      app: ivolve-db                   # Firewall protects the MySQL pod

    - Ingress

1. The Complete Declarative Jenkinsfile
📄 Jenkins/Lab21/Jenkinsfile Open ↗ 📄 Jenkins/Lab21/k8s.yaml Open ↗ 
pipeline {
    agent any

    environment {
        APP_NAME     = 'ivolve-demoapp'
        REGISTRY     = 'abdalrahmanx'
        IMAGE_NAME   = "${REGISTRY}/${APP_NAME}"
        DOCKER_CREDS = 'dockerhub'
        KUBECONFIG   = credentials('kubeconfig')
    }

    stages {
        stage('1. Build app') {
            steps {
                dir('Jenkins/Lab21/DemoApp') {
                    // -B: Batch mode (disables interactive prompts & progress spinner animation)
                    // clean: Deletes previous target/ build artifacts
                    // package: Compiles code, runs unit tests, packages into JAR
                    sh 'mvn -B clean package'
                }
            }
        }

        stage('2. Build Docker Image') {
            steps {
                dir('Jenkins/Lab21/DemoApp') {
                    // -t <name:tag>: Names and tags the image with the unique Jenkins BUILD_NUMBER
                    // .            : Build context path containing Dockerfile and compiled JAR
                    sh "docker build -t ${IMAGE_NAME}:${BUILD_NUMBER} ."
                }
            }
        }

        stage('3. Scan Docker Image') {
            steps {
                // --severity HIGH,CRITICAL: Limits vulnerability report to actionable high-risk flaws
                // --exit-code 0           : Runs security audit in non-blocking advisory mode so pipeline completes
                sh "trivy image --severity HIGH,CRITICAL --exit-code 0 ${IMAGE_NAME}:${BUILD_NUMBER}"
            }
        }

        stage('4. Push image to DockerHub') {
            steps {
                withCredentials([usernamePassword(credentialsId: DOCKER_CREDS,
                                                  usernameVariable: 'USER',
                                                  passwordVariable: 'PASS')]) {
                    // --password-stdin: Pipes secret from standard input avoiding shell history leakage
                    // -u <user>       : Docker Hub account username
                    sh "echo \$PASS | docker login -u \$USER --password-stdin"
                    sh "docker push ${IMAGE_NAME}:${BUILD_NUMBER}"
                }
            }
        }

        stage('5. Delete image locally') {
            steps {
                // rmi: Removes local image from Jenkins host to prevent hard drive saturation
                sh "docker rmi ${IMAGE_NAME}:${BUILD_NUMBER}"
            }
        }

        stage('6. Update image in deployment file') {
            steps {
                // -i: Edits file in-place
                // s|old|new|g: Regex replaces the image tag in Kubernetes manifest with current build number
                sh "sed -i 's|image: ${IMAGE_NAME}:.*|image: ${IMAGE_NAME}:${BUILD_NUMBER}|g' Jenkins/Lab21/k8s.yaml"
            }
        }

        stage('7. Deploy to Kubernetes cluster') {
            steps {
                // --kubeconfig: Passes authenticated ServiceAccount credentials from Lab 19
                // -f          : Specifies target Kubernetes manifest file
                sh "kubectl --kubeconfig \$KUBECONFIG apply -f Jenkins/Lab21/k8s.yaml"
                // rollout status: Blocks pipeline execution until deployment update reaches Ready state
                sh "kubectl --kubeconfig \$KUBECONFIG rollout status deployment/demoapp -n ivolve"
            }
        }
    }

The Core Idea & Concepts

  • Clean Hand-Off: Jenkins builds and publishes the container image, updates the image tag in Jenkins/Lab21/k8s.yaml, and executes git push. Argo CD detects the commit and rolls out the change.
  • Self-Healing: If an engineer manually alters a pod or deployment via kubectl, Argo CD detects the drift and immediately restores the manifest from Git.

The Core Idea & Concepts

Playbooks are YAML files describing the state target servers should be in. Each play defines target hosts (hosts: all), privilege escalation (become: true), and an ordered list of tasks:

  • Keyring Management: Modern Debian and Ubuntu deprecated apt-key add. Third-party repository keys must now be converted to binary format and saved under /usr/share/keyrings/, referenced with signed-by in the repo definition.

1. Author the Playbook (site.yml)
---
# Target all hosts listed in inventory
- hosts: all
  # Sudo escalation so tasks can install system packages and write /usr/local/bin
  become: true
  # Collect host architecture, OS distribution, and network facts for module use
  gather_facts: true

  tasks:
    # --- TASK 1: DOCKER RUNTIME ---
    - name: install docker
      ansible.builtin.apt:
        # Standard Ubuntu/Debian Docker runtime and CLI package
        name: docker.io
        # Idempotent state: installs if missing, skips if already present
        state: present
        # Runs apt-get update first so fresh containers don't fail on missing indices
        update_cache: true

    # --- TASK 2: JENKINS DEPENDENCIES ---
    - name: install java and gnupg (jenkins dependencies)
      ansible.builtin.apt:
        name:
          # Jenkins 2.x requires Java 17+ (headless avoids pulling 300MB of GUI/X11 libraries)
          - openjdk-17-jre-headless
          # Needed for gpg binary to dearmor repository keys into binary format
          - gnupg
        # Ensures both packages are installed; skips if already satisfied
        state: present

    # --- TASK 3: JENKINS GPG REPOSITORY KEY ---
    # Fetch 2026 key — the historical 2023 key expired in March 2026 and causes apt NO_PUBKEY errors
    - name: add jenkins repository key
      ansible.builtin.get_url:
        # Official Jenkins stable signing key URL
        url: https://pkg.jenkins.io/debian-stable/jenkins.io-2026.key
        # Destination file for ASCII-armored key
        dest: /usr/share/keyrings/jenkins-keyring.asc
        # Standard read permissions for root and apt service accounts
        mode: "0644"
        # Overwrite destination file to replace expired keys
        force: true

    # --- TASK 4: DEARMOR KEYRING TO BINARY ---
    # APT signed-by expects binary OpenPGP (.gpg), not ASCII-armored (.asc)
    - name: dearmor the jenkins key
      # gpg --dearmor converts ASCII armor to binary; --yes overwrites without prompting
      ansible.builtin.command: "gpg --dearmor --yes -o /usr/share/keyrings/jenkins-keyring.gpg /usr/share/keyrings/jenkins-keyring.asc"
      args:
        # Idempotency guard: skips execution if binary file already exists (returns changed=0)
        creates: /usr/share/keyrings/jenkins-keyring.gpg

    # --- TASK 5: JENKINS APT REPOSITORY ---
    - name: add jenkins repository
      ansible.builtin.apt_repository:
        # signed-by restricts key trust exclusively to this repository, preventing apt-key poisoning
        repo: "deb [signed-by=/usr/share/keyrings/jenkins-keyring.gpg] https://pkg.jenkins.io/debian-stable binary/"
        # Adds repository entry if not already present
        state: present
        # Writes entry to /etc/apt/sources.list.d/jenkins.list instead of main sources.list
        filename: jenkins

    # --- TASK 6: JENKINS SERVER PACKAGE ---
    - name: install jenkins
      ansible.builtin.apt:
        # Package pulled from the newly registered Jenkins APT repository
        name: jenkins
        # Installs package and registers systemd/init service
        state: present

    # --- TASK 7: STANDALONE KUBECTL BINARY ---
    # Fetch standalone binary directly into PATH, avoiding the overhead of the Google cloud apt repo
    - name: install kubectl
      ansible.builtin.get_url:
        # Official Kubernetes release binary URL for amd64 Linux
        url: https://dl.k8s.io/release/v1.33.13/bin/linux/amd64/kubectl
        # Placed directly in system executable directory accessible by all users
        dest: /usr/local/bin/kubectl
        # rwxr-xr-x: grants execute permissions so non-root users can run kubectl
        mode: "0755"

Encrypted Secret vault.yml $ANSIBLE_VAULT;1.1;AES256
➔ --vault-password-file ➔
MySQL Role tasks/main.yml community.mysql modules
➔ Grants ivolveuser ➔
Verified DB ivolve Database SHOW DATABASES ok

Step-by-Step Solution & Commands

1. Create Encrypted Vault File
# Create group_vars directory:
mkdir -p group_vars/all

# Create and encrypt the vault file:
ansible-vault create group_vars/all/vault.yml

Define the database password inside the encrypted file:

# AES-256 encrypted string created with ansible-vault
# Decrypted in memory at runtime via --vault-password-file; never written plaintext to disk
vault_mysql_password: "SuperSecretPassword123!"
2. Author the MySQL Role (roles/mysql/tasks/main.yml)
---
# python3-pymysql is required on the target node so Ansible community.mysql modules can run
- name: install mysql server and pymysql
  ansible.builtin.apt:
    name:
      - mysql-server     # MySQL database server daemon
      - python3-pymysql  # Python MySQL driver required by community.mysql modules
    state: present
    update_cache: true   # Refresh package index before installation

# Sysvinit service start: needed because Docker lab containers don't run systemd PID 1
- name: start mysql
  ansible.builtin.command: service mysql start
  # changed_when: false prevents marking this task as changed on every run (preserves idempotency)
  changed_when: false

# Creates schema; connects locally as root via Unix socket without password
- name: create the ivolve database
  community.mysql.mysql_db:
    name: ivolve
    state: present       # Idempotent: creates database only if it does not exist
    login_unix_socket: /var/run/mysqld/mysqld.sock  # Auth socket authentication for local root

# Provisions database user with credentials resolved from Ansible Vault
- name: create ivolveuser with all privileges on ivolve
  community.mysql.mysql_user:
    name: ivolveuser
    host: "%"            # Wildcard host: allows connections from any IP/container
    password: "{{ vault_mysql_password }}"  # Variable decrypted in-memory from group_vars/all/vault.yml
    priv: "ivolve.*:ALL" # Restricts full permissions strictly to ivolve database tables
    state: present       # Idempotent: creates user or updates password if changed
    login_unix_socket: /var/run/mysqld/mysqld.sock

# Verification task: connects as the newly created user using the vault password
- name: validate - connect as ivolveuser and list databases
  community.mysql.mysql_info:
    login_user: ivolveuser
    login_password: "{{ vault_mysql_password }}"
    login_host: 127.0.0.1  # TCP loopback connection to test remote grant
    filter: databases      # Restricts query to database list
  register: dbcheck        # Captures module output dictionary into variable
  changed_when: false      # Read-only query; never alters database state

# Print visible databases to confirm user grants are working
- name: show validation result
  ansible.builtin.debug:
    msg: "databases visible to ivolveuser: {{ dbcheck.databases | list }}"
3. Playbook Configuration (site.yml)
---
- hosts: all
  become: true
  vars_files:
    # Loads AES-256 encrypted variables into playbook scope
    - group_vars/all/vault.yml
  roles:
    # Runs MySQL provisioning role with vault variables available
    - mysql
4. Execute Playbook with Vault Credentials
# Run playbook supplying vault password file:
#   --vault-password-file : Path to file containing decryption key
ansible-playbook -i inventory site.yml --vault-password-file .vault-pass
5. Verify Connectivity as the New User
# Connect directly using ivolveuser credentials:
mysql -u ivolveuser -p -h 127.0.0.1 -e "SHOW DATABASES;"
Database information_schema ivolve performance_schema

Tips

  • Python MySQL Dependency: The community.mysql.mysql_db and mysql_user modules require python3-pymysql to be installed on the managed target node to interact directly with MySQL sockets.
  • Vault Password Protection: Never commit the .vault-pass file to Git. Add .vault-pass to your .gitignore and restrict file permissions with chmod 600 .vault-pass.

☁️ Automated Host Discovery with AWS EC2 Dynamic Inventory

Objective: Implement cloud-native host discovery using the amazon.aws.aws_ec2 dynamic inventory plugin to manage AWS EC2 instances filtered by tags.

Dynamic InventoryAWS EC2amazon.awsCloud Automation
📋 Lab Prompt & Requirements (Slide Task)
  • Configure AWS dynamic inventory using amazon.aws.aws_ec2 plugin.
  • Filter instances dynamically tagged Server=ivolve.
  • Execute Ansible ad-hoc commands and playbooks against dynamically discovered cloud instances.
  • Terminate cloud instances cleanly after verification.

The Core Idea & Concepts

In cloud environments, static IP inventories don't scale because servers launch, stop, or change IPs dynamically. Dynamic Inventory plugins (like amazon.aws.aws_ec2) query the AWS API at runtime, discover active instances matching specific tags (e.g. Server=ivolve), and hand their public IPs directly to Ansible.

Architecture & Workflow Flowchart

Plugin aws_ec2.yml amazon.aws plugin
➔ AWS API Call ➔
AWS Cloud Tag: Server=ivolve Discovers Running IPs
➔ Dynamic Inventory ➔
Playbook Run ec2.yml Docker Installed on Cloud

Step-by-Step Solution & Commands

1. Prerequisites: AWS SDK and Ansible Collection
# Install Python AWS SDK:
pip install boto3 botocore

# Install official Ansible AWS collection:
ansible-galaxy collection install amazon.aws
2. Launch EC2 Instance with Target Tag
# Launch Amazon Linux 2023 instance tagged Server=ivolve:
# (Ensure security group allows port 22 SSH from your IP)
aws ec2 run-instances   --image-id ami-0084a47cc718c111a   --count 1   --instance-type t3.micro   --key-name nti-devops-key   --security-group-ids sg-0eae4711e8c34c6eb   --tag-specifications 'ResourceType=instance,Tags=[{Key=Server,Value=ivolve}]'
3. Configure Dynamic Inventory (aws_ec2.yml)

Note: The filename must end with aws_ec2.yml or aws_ec2.yaml.

# AWS EC2 dynamic inventory configuration. Filename must end with aws_ec2.yml or aws_ec2.yaml.
plugin: amazon.aws.aws_ec2
regions:
  # AWS region where target EC2 instances are provisioned
  - eu-central-1
filters:
  # Filter: only discover instances tagged Server=ivolve, ignoring other VPC workloads
  tag:Server: ivolve
  # Filter: only target active, running instances (ignores stopped/terminated nodes)
  instance-state-name: running
hostnames:
  # Use public IPv4 address as inventory_hostname so Ansible dials over SSH
  - ip-address
vars:
  # Default SSH username for Amazon Linux 2023 AMIs
  ansible_user: ec2-user
  # SSH private key matching the AWS Key Pair used at launch
  ansible_ssh_private_key_file: /root/.ssh/nti-devops-key.pem
  # Explicit Python 3 interpreter path on Amazon Linux 2023
  ansible_python_interpreter: /usr/bin/python3
4. Query Live Cloud Inventory
# Test discovery graph from AWS API:
#   --graph : Outputs discovered host hierarchy
ansible-inventory -i aws_ec2.yml --graph
@all: |--@ungrouped: |--@aws_ec2: | |--3.75.247.89
5. Execute Playbook Against Discovered Cloud Instances (ec2.yml)
---
# Play targets all dynamically discovered EC2 instances from aws_ec2.yml
- hosts: all
  # Sudo escalation so dnf and systemd commands can run as root
  become: true
  tasks:
    # Amazon Linux 2023 uses dnf instead of yum or apt
    - name: install docker
      ansible.builtin.dnf:
        name: docker     # Official Docker package in Amazon Linux 2023 repos
        state: present   # Idempotent: ensures package is installed

    # Service configuration via systemd
    - name: start and enable docker
      ansible.builtin.service:
        name: docker     # Docker systemd service unit
        state: started   # Ensures daemon is running (starts if stopped)
        enabled: true    # Configures systemd to start Docker on system reboot

    # Verification: check installed Docker version on cloud instance
    - name: docker version
      ansible.builtin.command: docker --version
      register: dv         # Captures command stdout, stderr, and return code
      changed_when: false  # Read-only check: skips marking task as changed

    # Print output with hostname to confirm successful execution across cloud nodes
    - name: show result
      ansible.builtin.debug:
        msg: "{{ ansible_hostname }} -> {{ dv.stdout }}"
# Run playbook against discovered instances:
ansible-playbook -i aws_ec2.yml ec2.yml
ok: [3.75.247.89] => { "msg": "ip-172-31-21-200 -> Docker version 25.0.14, build 0bab007" } PLAY RECAP ********************************************************************* 3.75.247.89 : ok=5 changed=2 unreachable=0 failed=0
6. Terminate Cloud Resources
# Clean up EC2 instance:
aws ec2 terminate-instances --instance-ids <INSTANCE_ID>

Tips

  • Naming Requirement: The inventory configuration file must end in aws_ec2.yml or aws_ec2.yaml. Ansible uses the filename pattern to identify and invoke the dynamic inventory plugin.
  • Connection Variables: In plugin inventories, define connection variables (like ansible_user and private key path) directly within the plugin's vars: block so they reliably attach to dynamically discovered hosts.
